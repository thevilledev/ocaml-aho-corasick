Compatibility

Aho–Corasick is one algorithm, but "the matches" is not one answer. Libraries differ on whether overlapping matches are reported, on how a non-overlapping subset is chosen, on whether an end offset is inclusive or exclusive, and on whether offsets count bytes or characters. A scanner ported between two of them without checking these will run, produce plausible output, and be wrong.

This page states where this library sits on each axis, so that agreement or disagreement with another implementation is a fact you can look up rather than discover in production.

What "compatible" means here. The semantics are specified and checked against an independent oracle in CI. They are not checked against another Aho–Corasick library by any automated harness. Where this page says two implementations agree, that is a reading of their documented behaviour, not a test result — which is why the conformance vectors below exist.

The three match kinds

The clearest vocabulary for these comes from the Rust aho-corasick crate, whose MatchKind names three behaviours. Take the patterns Sam and Samwise, in that order, and the input Samwise:

Where this library sits
Kind Rule Here
Standard Every occurrence, overlaps included. find_all, find_iter, Stream.feed
Leftmost-first Leftmost match; ties go to the pattern given earlier. not provided
Leftmost-longest Leftmost match; ties go to the longest. find_leftmost_longest, replace_all

Leftmost-first is the one to watch when porting, because it is the only kind whose answer depends on the order you listed the patterns in. Give the same two patterns as ["Samwise"; "Sam"] and a leftmost-first search reports Samwise instead. Nothing in this library is order-sensitive that way: pattern order affects only the pattern index in the results and the tie-break between duplicate patterns.

The three kinds correspond to how regex engines resolve Sam|Samwise: a Perl-style engine takes the first alternative that matches, a POSIX engine takes the longest. If you are replacing a regex alternation of literals with this library, find_leftmost_longest matches the POSIX behaviour and there is no equivalent of the Perl one.

One trap inside "standard"

A non-overlapping search under standard semantics is not leftmost-longest. The Rust crate documents standard semantics as reporting matches "as they are seen", which means the match that ends first wins, and the search resumes after it. On Samwise that yields Sam, not Samwise. So a default-configured AhoCorasick::find_iter in Rust is not the counterpart of find_leftmost_longest here, even though both return a non-overlapping list. The counterpart is an automaton built with MatchKind::LeftmostLongest.

Offset conventions

The second thing that silently changes results. This library reports { start; stop } as a half-open byte range: stop is one past the last matched byte, so the length is stop - start.

What a match carries, and how to convert
Implementation Reports To get this library's start/stop
ocaml-aho-corasick { pattern; start; stop }, bytes, half-open —
Rust aho-corasick Match over a Span, documented as "the starting offset is inclusive while the ending offset is exclusive" identical: start(), end()
Python pyahocorasick iter() yields (end_index, value) where the end index is inclusive — its own documentation computes the start as end_index - len(value) + 1 start = end_index - len + 1, stop = end_index + 1
Hyperscan the match callback receives an end offset; the start offset is supplied only for patterns compiled with HS_FLAG_SOM_LEFTMOST check the engine's own convention before converting

An off-by-one here is invisible in unit tests that only ask "did it match" and catastrophic in a redactor, which will leave the last byte of every secret on the page. The vectors below catch it on the first row.

Mapping to the Rust crate

The Rust crate is the most complete implementation in general circulation, so it makes the most useful reference point.

Nearest counterpart, given a matching MatchKind
Here Rust aho-corasick Notes
build patterns AhoCorasick::new Both take patterns in order; the index is the pattern id.
build ~ignore_case:true ascii_case_insensitive(true) Both fold ASCII only.
find_all, find_iter find_overlapping_iter, with MatchKind::Standard Report order is specified here; sort if you depend on it there.
find_leftmost_longest find_iter, with MatchKind::LeftmostLongest Not the default kind — you must ask for it.
replace_all replace_all, with MatchKind::LeftmostLongest Same selection; Rust takes a replacement per pattern, not a closure.
mem is_match Both stop at the first match.
Stream.feed stream_find_iter, with MatchKind::Standard Not identical: Rust's stream iterator is non-overlapping, this one reports overlaps.
— MatchKind::LeftmostFirst No counterpart here.

The two libraries also agree on a structural restriction, and for the same reason: leftmost semantics need lookahead, so they cannot be offered over a stream or combined with overlapping search. Rust makes that a runtime error; here it is simply absent from the interface.

Porting checklist

Run down this list when moving a pattern set between implementations. Each line is a real behavioural difference, not a style preference.

  1. End offset. Exclusive here. Inclusive in pyahocorasick. Convert, do not assume.
  2. Bytes or characters. Offsets here count bytes. An implementation that indexes characters will disagree on any input with a multi-byte character before the match.
  3. Which kind. Overlapping, leftmost-first or leftmost-longest. Pick deliberately; the default differs by library.
  4. Pattern order. Irrelevant here, decisive under leftmost-first.
  5. Duplicate patterns. Reported once per index here. An implementation backed by a set or dictionary may collapse them, losing one of your ids.
  6. Case folding. ASCII A to Z only. Anything advertising "case-insensitive" over Unicode will match strictly more.
  7. Report order. Specified here as end offset, then longest, then pattern index. Sort both sides before comparing if the other implementation makes no promise.
  8. Streaming. Available here for overlapping matches only, with absolute offsets and nothing to flush.

Conformance vectors

These are the answers this library gives. They are small on purpose: each one isolates a decision that implementations differ on, so a disagreement points straight at the cause. Offsets are half-open byte offsets, and name@a..b means the pattern name matched s[a..b).

Each row is a decision point. Rows 1 and 3 separate overlapping from non-overlapping search. Rows 1 and 4 separate leftmost-longest from leftmost-first and from "first match seen". Row 7 shows whether duplicate patterns survive as distinct ids (x#0 and x#1 are the two pattern indices). Row 9 checks that ASCII folding happens at all; it will not tell you whether the other implementation also folds beyond ASCII, so check that separately with É against é. Row 10 fails immediately on any implementation that indexes characters instead of bytes.

Streaming has one vector of its own. With the single pattern abc and the input fed as "xxab" then "c-abc", the first feed reports nothing and the second reports abc@2..5 and abc@6..9: absolute offsets, and the boundary-crossing match found. An implementation that reports offsets relative to each chunk, or that misses the first match, will differ here and nowhere else.

What is not claimed

No differential test runs this library against the Rust or Python implementations. The table above is a careful reading of their documentation, checked against the behaviour those documents specify; it is not a CI job, and either side may have bugs the other does not. Treating agreement as established would be exactly the kind of unverified claim this page exists to avoid.

If you do run the vectors against another implementation and find a disagreement, open an issue with the pattern set, the input and both outputs. A disagreement is either a bug here or a difference worth documenting on this page.
